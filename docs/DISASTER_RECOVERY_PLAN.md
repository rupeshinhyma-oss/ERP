# Disaster Recovery & Operational Resilience Plan

**Ecosystem:** Multi-ERP Platform (`ERP_Main`, `Yinglima_ERP`, `Inhyma_ERP`)  
**Database Infrastructure:** Supabase PostgreSQL  
**Recovery Objectives:**
- **Recovery Time Objective (RTO):** < 15 minutes (Critical APIs), < 1 hour (Full Analytics/Projections)
- **Recovery Point Objective (RPO):** < 1 minute (Supabase Point-in-Time Recovery / Transactional Outbox)

---

## 1. Disaster Recovery Scenarios & Playbooks

### Scenario A — Control Plane Outage (`ERP_Main` Down)
- **Impact:** Global login, global federation launcher, cross-ERP multi-entity search, and global aggregated reporting are temporarily unavailable.
- **Architectural Invariant:** **Partner ERPs MUST continue normal local business operations.**
- **Local Application Behavior:**
  - Local direct login (`POST /api/v1/auth/login`) in Yinglima ERP and Inhyma ERP continues to operate normally using local Argon2id credentials.
  - Sourcing, RFQs, quotations, supplier management, production planning, and task execution proceed uninterrupted.
  - Outbox events generated by local business transactions are saved locally with status `PENDING`.
  - The local outbox publisher attempts dispatch to `ERP_Main/backend/app/integration/events`; upon receiving connection errors or HTTP 503, it enters exponential backoff without blocking the user.
- **Recovery Procedure:**
  1. Restore `ERP_Main` container pods (`kubectl rollout restart deployment/erp-main-api`).
  2. Verify `GET /api/v1/health/ready` returns 200 OK.
  3. Partner ERP outbox dispatchers resume event transmission automatically.
  4. Run `POST /api/v1/global/projections/rebuild` to catch up read-model checkpoints.

---

### Scenario B — Partner ERP Outage (`Yinglima_ERP` Down)
- **Impact:** Yinglima procurement and sourcing workflows unavailable.
- **System Isolation:**
  - `Inhyma_ERP` remains 100% operational; production planning and Indian distribution are unaffected.
  - `ERP_Main` remains fully operational. Global search continues serving cached/materialized projections of Yinglima buyers/suppliers.
  - Telemetry reconciliation in `ERP_Main` reports honest status `UNKNOWN` for Yinglima ERP without crashing or blocking Inhyma reconciliation.
- **Recovery Procedure:**
  1. Restore Yinglima web and worker pods.
  2. Check queue health: `GET /api/v1/health/ready`.
  3. Worker resets any stuck jobs older than 30 minutes.
  4. Dispatch pending outbox backlog.

---

### Scenario C — Partner ERP Outage (`Inhyma_ERP` Down)
- **Impact:** Inhyma planning and task management unavailable.
- **System Isolation:**
  - `Yinglima_ERP` and `ERP_Main` operate with zero disruption.
  - Sourcing RFQs and global dashboards remain online.
- **Recovery Procedure:**
  1. Restore Inhyma containers.
  2. Trigger queue drain and outbox catch-up.

---

### Scenario D — Database / Supabase Cloud Outage
- **Detection:**
  - Kubernetes readiness probes (`GET /api/v1/health/ready`) fail with HTTP 503 Service Unavailable.
  - Applications log `asyncpg.exceptions.CannotConnectNowError` or connection timeouts.
- **Application Behavior:**
  - Connection pool pre-ping detects dead connections and retries up to 5 times with exponential backoff (`DATABASE_CONNECT_RETRIES=5`, `DATABASE_CONNECT_RETRY_DELAY_SECONDS=2.0`).
  - Web handlers fail gracefully with user-facing HTTP 503: `"Database connectivity temporarily unavailable. Please retry shortly."`
  - Zero application crash loops.
- **Supabase Point-in-Time Recovery (PITR) & Restore Procedure:**
  1. Navigate to Supabase Dashboard -> Project Settings -> Database -> Backups.
  2. For Point-in-Time Recovery (PITR): select the desired restore point prior to the incident.
  3. Alternatively, trigger restore from the latest automated physical backup dump using `pg_restore`:
     ```bash
     pg_restore -d "$DIRECT_URL" -v erp_backup.dump
     ```
  4. Once restored, verify application connectivity and migrations via `alembic upgrade head`.
  5. Restart application pods to re-establish active connection pools.
  6. Verify data integrity across `alembic_version`, users, and outbox tables.

---

### Scenario E — Failed Application Deployment
- **Detection:**
  - Post-deployment smoke tests report HTTP 500 errors or readiness probes fail.
- **Immediate Rollback Sequence:**
  ```text
  1. Detect Deployment Failure
          ↓
  2. Halt Deployment Pipeline Immediately
          ↓
  3. Roll Back Application Container to Revision N-1:
     kubectl rollout undo deployment/erp-main-api
          ↓
  4. Check Database Schema Compatibility:
     - If non-destructive (Expand phase): No DB rollback required!
     - If destructive migration ran: Apply targeted Alembic downgrade:
       alembic downgrade -1
          ↓
  5. Verify Readiness Probes Return HTTP 200 OK
          ↓
  6. Post-Mortem & Incident Logging
  ```

---

### Scenario F — Corrupted or Stale Integration Data Recovery
- **Problem:** Data inconsistency between source ERP outbox and ERP_Main projection tables caused by network drop or out-of-order delivery.
- **Resolution Strategy:**
  1. **Audit Scope:** Run `POST /api/v1/global/reconciliation/erps/{erp_id}` to detect projection divergence (`RECONCILIATION_REQUIRED`).
  2. **Dead-Letter Queue Inspection:** Query `GET /api/v1/internal/integration/dead-letters` to inspect rejected payloads and stack traces.
  3. **Event Replay:** Re-ingest uncorrupted events from partner outbox. Because `ERP_Main` enforces idempotency (`UNIQUE(event_id)`), re-sending already-processed events is 100% safe (`duplicate: true`).
  4. **Projection Index Rebuild:** Execute `POST /api/v1/global/projections/rebuild` to deterministically replay inbox events and refresh materialized views.

## 2. Backup & Point-in-Time Recovery Validation Drill

### Verification Drill Steps:
1. **Point-in-Time Recovery (PITR) Validation Test:**
   - Supabase continuous WAL archiving & PITR restoration test.
   - Tested database startup against point-in-time recovery target.
2. **Cold Backup Dump Test:**
   - Tested `pg_dump` schema and data extraction:
     ```bash
     pg_dump -d "$DIRECT_URL" -F c -b -v -f erp_backup.dump
     ```
3. **Cold Backup Restore Test:**
   - Restored into clean test database:
     ```bash
     pg_restore -d "$NEW_DATABASE_URL" -v erp_backup.dump
     ```
4. **Integrity Validation:**
   - Verified row counts in `users`, `erp_instances`, `buyers`, `suppliers`, and `outbox_events` match source database with zero loss.
